# Feature: Повторная обработка вакансий

## Status

`DONE`

## Goal

Повторять вакансии из дневных отчётов по прямой ссылке, не проходя выдачу заново, и явно выбирать канал запуска, не
правя конфиг ради одного прогона.

## Requirements

### Functional requirements

1. `-r`, `--retry` и `--re` повторяют вакансии со статусами `pipeline.retry.statuses` (без значения) или с указанным
   статусом, поиск и выдача не используются
2. Один запуск работает с одним каналом: поведение не меняется, параллельной обработки двух сайтов нет
3. Канал запуска выбирается необязательной опцией `--channel <CHANNEL>` с псевдонимом `--ch`. Допустимые
   значения `<CHANNEL>`: `hh` и `habr`, далее по тексту для простоты: `--ch`
4. Без опции `--ch` канал берётся из `search.channel`. Дефолт схемы остаётся `hh`: конфиг — единственное место, где
   живёт значение по умолчанию
5. Опция `--ch` действует одинаково как для обычного запуска, так и для `--retry` и для `--login`: выбранный канал
   определяет сессию, браузерный профиль, выдачу, селекторы страницы вакансии и тексты причин
6. Записи другого канала при повторе не выбираются: они не попадают ни в счётчики запуска, ни в консоль. Их число
   пишется в jsonl одним событием `retry_channel_mismatch` с полем `message`
7. Неверное значение `<CHANNEL>` — ошибка разбора аргументов до запуска браузера
8. В логе видно выбранный канал и источник выбора: опция или конфиг
9. Повтор идёт резюме текущего запуска: резюме из записи отчёта не подставляется. Если запись сделана
   другим резюме и записи текущего резюме по этой вакансии ещё нет, вакансия обрабатывается один раз резюме
   запуска. Если запись текущего резюме уже есть, повтор пропускается с событием `retry_profile_mismatch`
   и полем `message`, чтобы не отправлять повторный отклик на ту же вакансию
10. Число в строке «Повторная обработка по отчётам» и в событии `retry_selected` — это записи выбранного канала,
    которые повтор возьмёт. Архивные вакансии в число не входят: архив терминальный. Поэтому число сходится с
    веб-отчётом для того же статуса и источника

### Limitations

- Смешанный повтор (оба канала за один запуск) не входит в эту задачу: это отдельная доработка с последовательными
  сессиями
- Опция не переписывает записи отчёта и их поле `channel`
- Опция не влияет на `--install-browser` и `--notify-test`: они не связаны с каналом поиска
- Публичные ключи конфига не меняются, новый ключ не добавляется

## Acceptance Criteria

- [x] `--retry --help`, `--retry -h` и `-r -h` печатают справку своей опции
- [x] `--retry --ch habr` повторяет записи career.habr.com, записи hh.ru пропускает
- [x] `--ch hh --re` при `search.channel: habr` работает так же, как обычный запуск c hh.ru
- [x] Без опции поведение совпадает с текущим: канал из `search.channel`
- [x] `--ch superjob --re` завершается ошибкой аргументов, браузер не запускается
- [x] Выбранный канал используется на всех шагах повторов: сессия, выдача, страница вакансии, причины
- [x] В логе есть событие повтора с выбранным каналом и источником выбора
- [x] Число в строке «Повторная обработка по отчётам» сходится с веб-отчётом для выбранного статуса и источника
- [x] Архивные вакансии повтор не берёт и в число повтора не входят
- [x] У событий пропуска `retry_profile_mismatch` и `retry_channel_mismatch` есть поле `message`
- [x] Для всех команд и опций повторов выше есть справка, которая выводится по командам: `--help` и `-h`
- [x] Тесты CLI и pipeline на фейковом канале проходят без браузера
- [x] Повтор не создаёт дубликатов, число попыток растёт, остановка не теряет данные
- [x] Параллельный запуск с другим резюме не падает на записи чужого резюме: вакансия обрабатывается
  резюме запуска, повторный отклик по ней не отправляется
