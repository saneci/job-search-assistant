# hh-agent

Персональный агент автоматических откликов на hh.ru. Работает по требованию: запустил → выполнил цикл →
завершился. Браузерная автоматизация (Playwright + Chromium), оценка вакансий и генерация писем через
LLM (AITUNNEL), отчёт на email.

## Что делает

1. Открывает Chromium и восстанавливает сохранённую сессию hh.ru (при первом запуске — ручной вход).
2. Поднимает резюме в поиске («Поднять в поиске»), если с прошлого подъёма прошло
   `resume.boost_interval_hours` часов (по умолчанию 4); отметка хранится в `data/cache.json`.
3. Ищет вакансии по запросам из `config.yaml` с фильтрами (регион, зарплата, опыт, график).
4. Отфильтровывает вакансии по стоп-словам в названии (без LLM).
5. Открывает каждую вакансию, извлекает полный текст описания.
6. Вакансии с тестами, анкетами и внешними формами не откликаются, а попадают
   в дневной отчёт `data/report/<дата>.json` со статусом `queued` и понятной причиной.
7. Decision-вызов LLM возвращает вероятность «подходит»; отклик отправляется при `P > threshold`.
8. Generation-вызов пишет сопроводительное письмо в стиле пользователя (JSON с валидацией).
9. Нажимает «Откликнуться», вставляет письмо, отправляет отклик (с паузами и дневным лимитом).
10. Формирует отчёт: консоль, `logs/<run_id>.json` и (опционально) email.

## Установка

Требуется Python 3.11+ (проверено на 3.15.1). Все зависимости ставятся готовыми wheels — **компилятор C++ не нужен**:
YAML читается чистым Python-парсером `ruamel.yaml`.

```bash
py -m venv .venv
.venv\Scripts\python.exe -m pip install -r requirements.txt   # Windows
# python3 -m venv .venv && .venv/bin/pip install -r requirements.txt   # macOS/Linux
```

Браузер:

- по умолчанию `browser.channel: chrome` — используется **уже установленный Google Chrome**,
  ничего скачивать не нужно;
- если Chrome нет, поставьте `browser.channel: ""` и выполните
  `.venv\Scripts\python.exe -m playwright install chromium` (или `python run.py --install-browser`).

На Windows проще запускать `run.bat` (двойной клик), в Git Bash / WSL / Linux — `sh run.sh`:
оба скрипта сами найдут Python, создадут `.venv`, поставят зависимости и браузер.

## Настройка

1. Скопируйте `.env.example` в `.env` и укажите `AITUNNEL_API_KEY`.
2. Отредактируйте `config.yaml`:
    - `search_query` — строка или список запросов;
    - `area` — название региона (`Москва`, `Россия`, …) или числовой id hh.ru;
    - `salary_from`, `experience`, `schedule` — необязательные фильтры; `experience` принимает
      одно значение или список (`between1And3`, `between3And6`, …) — список отмечает несколько
      чекбоксов в фильтре «Опыт» на hh.ru;
    - `exclude_keywords` — стоп-слова в названии вакансии;
    - `exclude_companies` — компании, на вакансии которых не откликаемся (подстрока, без учёта регистра);
    - `limit_per_run` — максимум откликов за запуск (старый ключ `daily_limit` тоже принимается);
    - `cover_letter_max_length` и `cover_letter_signature` — лимит длины письма и подпись с контактами
      (дописывается в конец через пустую строку, входит в лимит; LLM её не пишет — дубли исключены);
    - `delay_between_actions` — случайная пауза между действиями;
    - `pages_limit` и `per_page` — глубина выдачи: hh.ru отдаёт 20 карточек на страницу, поэтому
      глубина = `pages_limit × 20` (больше 20 `per_page` не имеет смысла: hh сдвинет страницы
      и часть вакансий потеряется);
    - `browser.channel` — `chrome` / `msedge` (установленный браузер) или `""` (Chromium от Playwright);
    - `browser.captcha_wait_seconds` — сколько секунд ждать, пока вы вручную решите капчу
      в открытом окне браузера (по умолчанию 120; `0` — не ждать). Капча не обходится:
      приложение только ждёт и продолжает отклик, если вы её прошли;
    - `paths` — где лежат профиль, сессия, кэш подъёма резюме, дневные отчёты (`report_dir`) и логи;
    - `resume.name` — полное название резюме в списке резюме hh.ru; пусто — подъём не выполняется;
    - `resume.boost_interval_hours` — как часто поднимать резюме в поиске (по умолчанию 4 часа);
    - `llm.decision` / `llm.generation` — базовые URL, модели и порог решения;
    - `llm.decision.criteria` — тексты критериев, которые уходят в Decisions API (`questions.fit.criteria`):
      модель решений сравнивает по ним профиль с вакансией и возвращает вероятности;
      `llm.decision.threshold` — числовая отсечка уже в приложении (`P("подходит") > threshold`).
      Оба значения живут только в конфиге, в промпте их нет;
    - `llm.decision.explain_rejections` — объяснять ли отказы отдельным дешёвым Chat-запросом
      (по умолчанию `false`: причина считается из вероятностей, без лишней оплаты);
    - `llm.system_prompt_path` — файл с системным промптом (`SYSTEM_PROMPT.md` по умолчанию;
      именно он, а не код, задаёт правила оценки и письма — файл обязателен).
    - `processed_retention_days` — сколько дней хранить дневные отчёты в `data/report`
      (при старте файлы старше этого срока удаляются, посторонние файлы не трогаются).
3. Отредактируйте профиль (`paths.profile`, по умолчанию `data/profile.md`): описание, стек, примеры писем
   и правила стиля. Примеры берутся из подраздела «Примеры», правила — из раздела «Стиль написания
   сопроводительных писем».
4. При необходимости отредактируйте `SYSTEM_PROMPT.md`: правила оценки, стиля, тона и **достоверности**
   (письмо должно содержать только факты из профиля), формат JSON-ответа. Это единственный источник
   системного промпта: правки применяются при следующем запуске, код менять не нужно; если файл удалить,
   запуск остановится с понятной ошибкой (в коде остаётся лишь аварийный мини-промпт на случай сбоя чтения).

Для писем на email сначала включите канал: `notifications.email.enabled: true`, заполните
`smtp_host`, `smtp_port`, `use_ssl`, `sender`, `recipient` и задайте `SMTP_PASSWORD`
(и при необходимости `SMTP_USERNAME`) в `.env`.

Виды писем настраиваются раздельно:
- `notifications.report.enabled` — письмо с отчётом после запуска;
- `notifications.captcha.enabled` — письма о капче;
- у каждого вида может быть свой `recipient` — если он не указан, письмо уходит на общий
  `notifications.email.recipient`.

Gmail: включите двухэтапную аутентификацию и создайте «пароль приложения» (аккаунт Google →
Безопасность → Пароли приложений), его и положите в `SMTP_PASSWORD`. Нужны `smtp_host: smtp.gmail.com`,
`smtp_port: 465`, `use_ssl: true`; `sender` и `recipient` могут быть одним и тем же адресом.
Проверка канала без запуска агента: `python run.py --notify-test` (по письму на каждый включённый вид).

Когда hh.ru показывает капчу (на странице поиска, вакансии или в форме отклика), приложение
присылает **одно** короткое письмо с темой `[hh-agent] Капча на hh.ru…`: вакансия, ссылка и что
сделать. Если капча в форме отклика и человек не успел за `browser.captcha_wait_seconds`,
второго письма нет — об остановке скажет отчёт (если включён `notifications.report`).
Капча не обходится: её решает человек.

Если `--notify-test` пишет «SMTP-сервер закрыл соединение», провайдер блокирует SMTP-вход
(так бывает у Gmail из некоторых сетей). Отправляйте через другой SMTP: `smtp_host: smtp.yandex.ru`
(или `smtp.mail.ru`), `sender` — адрес этого ящика, `SMTP_USERNAME` и `SMTP_PASSWORD` — логин и
пароль приложения от него. `recipient` может остаться Gmail: ограничение касается только отправки.

## Запуск

```bash
python run.py                     # обычный цикл; без state.json сначала попросит войти
python run.py --login             # только вход и сохранение сессии
python run.py --config config.yaml
python run.py --install-browser   # поставить Chromium, если не используется установленный браузер
python run.py --notify-test       # проверить канал уведомлений: одно письмо, без браузера и LLM
```

Или без ручной подготовки окружения:

- Windows: двойной клик по `run.bat`;
- Git Bash / WSL / Linux / macOS: `sh run.sh` (аргументы передаются в `run.py`, например `sh run.sh --login`).

Первый запуск открывает браузер: войдите в аккаунт hh.ru вручную и нажмите Enter в консоли.
Сессия сохраняется в `data/state.json` и восстанавливается при следующих запусках.
Остановить работу можно в любой момент по Ctrl+C: приложение сохранит сессию, допишет отчёт
и выведет итог: сколько откликов отправлено и почему работа остановилась.

### Как читать лог

Строки по вакансиям начинаются с её названия и компании, поэтому видно, к чему относится событие:

```
[2026-10-21 16:02:12] Java - разработчик — СберЛизинг (id=1234567): открываю вакансию
[2026-10-21 16:02:37] Java - разработчик — СберЛизинг (id=1234567): LLM-решение: «подходит» (порог 0.80, подходит=0.99, не подходит=0.01)
[2026-10-21 16:02:38] Java - разработчик — СберЛизинг (id=1234567): LLM-вердикт: Профиль совпадает с ключевыми требованиями...
[2026-10-21 16:02:39] Java - разработчик — СберЛизинг (id=1234567): отклик отправлен (всего 1 из 3)
```

`id` — номер вакансии hh.ru, по нему сразу видно, дубликат это или разные вакансии с одинаковым названием.
Метка времени — локальная зона; отчёт печатается без меток, время в JSONL — в поле `ts`.

Приветствие в письме гарантируется кодом: если модель не начала письмо со «Здравствуйте!»,
приложение добавляет его само и срезает случайный обрывок в начале (`3PL.` → `Здравствуйте! Мне интересна…`).
В консоль пишется `…: в письме не было приветствия, добавил «Здравствуйте!»`, в JSONL — `greeting_added: true`.

В `LLM-решение` выводится **вердикт приложения**: `подходит`, если `P("подходит")` выше
`llm.decision.threshold`, иначе `не подходит` (даже когда у модели вариант «подходит» набрал больше
голосов, например 0.57 против 0.43). Сырой выбор модели по максимальной вероятности — в поле
`model_choice`, вердикт приложения — в `llm_verdict`.

Одна и та же вакансия не обрабатывается дважды: дубликаты в выдаче (по id вакансии и по паре
«название + компания») отбрасываются со строкой «дубликат в выдаче, пропускаю».

Повторно не проходятся и вакансии из прошлых запусков: по каждому дню ведётся отчёт
`data/report/<дата>.json` и вакансия помечается строкой «уже обрабатывалась <дата>, пропускаю».
Отчёты старше `processed_retention_days` (по умолчанию 7 дней) удаляются при старте.

Файл читается как отчёт: `status` (`sent`, `skipped`, `queued`, `error`), а у пропусков и отложенных
вакансий ещё и `reason` — видно, почему вакансию не взяли:

```json
[
  {
    "url": "https://hh.ru/vacancy/138144810",
    "title": "Java junior разработчик интеграционных решений",
    "company": "Банк Русский Стандарт",
    "status": "skipped",
    "reason": "вероятность 0.57 не выше порога 0.80",
    "processed_at": "2026-10-21T16:02:12+03:00"
  },
  {
    "url": "https://hh.ru/vacancy/138144820",
    "title": "Java-разработчик",
    "company": "СберЛизинг",
    "status": "sent",
    "processed_at": "2026-10-21T16:05:41+03:00"
  },
  {
    "url": "https://hh.ru/vacancy/138144830",
    "title": "Java-разработчик",
    "company": "Тинькофф",
    "status": "queued",
    "reason": "Для отклика на вакансию необходимо пройти тестирование",
    "processed_at": "2026-10-21T16:09:02+03:00"
  }
]
```

Отдельного файла очереди нет: отложенные вакансии видны в том же дневном отчёте по `status: "queued"`,
и повторно они не проходятся — как и остальные записи файла дня.

Полный журнал событий — в `logs/<дата>.jsonl` (один файл на дату, перезапуски дописывают в конец;
принадлежность события к запуску — в поле `run_id`): URL, вероятности, длина письма и поле `llm_reason`
с причиной вердикта для одобрений и отказов (для отказов — из вероятностей, либо текст модели,
если включён `llm.decision.explain_rejections`); в `llm_reason_source` видно, откуда причина: `model`
или `threshold`. Текст сопроводительного письма, профиль и контакты в логи не пишутся — только
факты и длины.

### Отчёт

В конце запуска в консоль (и на email, если включён) печатается:

```
=================================
Отчёт за 2026-10-21 15:19
=================================
- Обработано вакансий: 12
- Отправлено откликов: 1
- Пропущено (не подошло): 7
- Отложено (тесты/анкеты): 0
- Причина остановки: достигнут лимит откликов за запуск (1)
- Длительность: 5 мин 31 с
```

Ниже — последние отправленные отклики и путь к файлу деталей `logs/<run_id>.json`
(в консоли путь печатается отдельной строкой с меткой времени, без метки — только в письме).

## Файлы

Всё, что приложение создаёт и изменяет, лежит в `data/` (каталог не попадает в git), логи — в `logs/`.
Пути настраиваются секцией `paths` в `config.yaml`.

| Файл                        | Назначение                                                                    |
|-----------------------------|-------------------------------------------------------------------------------|
| `config.yaml`               | настройки поиска, LLM и уведомлений                                           |
| `AGENTS.md`                 | соглашения проекта: принципы, промпт, логи, тесты                             |
| `SYSTEM_PROMPT.md`          | системный промпт LLM (`llm.system_prompt_path`): правила оценки, тона, письма |
| `data/profile.md`           | профиль пользователя для LLM (`paths.profile`)                                |
| `run.py`                    | точка входа приложения (аналог `main()`), запускается из `run.bat` / `run.sh` |
| `data/state.json`           | cookies + localStorage hh.ru (`paths.session_state`)                          |
| `data/cache.json`           | когда последний раз поднимали резюме в поиске (`paths.cache`)                 |
| `data/report/*.json`        | дневной отчёт: что отправлено, отложено и пропущено (`paths.report_dir`)      |
| `logs/<дата>.jsonl`        | события за дату (JSON Lines), включая решения LLM (`paths.logs_dir`)          |
| `logs/<run_id>.json`        | детальный отчёт запуска                                                       |
| `logs/<run_id>-error-N.png` | скриншот страницы при ошибке                                                  |

Причины отложенных вакансий (`status: "queued"`, поле `reason`):
`Для отклика на вакансию необходимо пройти тестирование`, `…необходимо заполнить анкету`,
`Отклик нужно отправить на сайте работодателя`, `Нужно заполнить сопроводительное письмо вручную`,
`hh.ru просит пройти капчу: откликнитесь вручную`,
`hh.ru не подтвердил отправку отклика — проверьте вакансию вручную` (код причины — в JSONL, поле `code`).
Если hh.ru показывает капчу, приложение ждёт ручного решения (см. `browser.captcha_wait_seconds`),
а скриншот состояния сохраняет в `logs/<run_id>-captcha.png`.

Когда отклик не подтвердился (`status: unknown`), в JSONL пишется событие `respond_state`:
`page_url`, текст формы отклика (`form_text`, без письма) и `letter_length` — по нему видно, что
именно показал hh.ru. Дополнительно сохраняется скриншот `logs/<run_id>-respond-unknown.png`,
а если снять его не удалось — событие `screenshot_error`.

## Возможные проблемы и способы их устранения

**Chrome обновился, и браузер перестал запускаться.** Playwright управляет установленным Chrome через CDP,
и очень крупные обновления Chrome иногда опережают установленную версию Playwright. Лечится без правок кода:

```bash
.venv\Scripts\python.exe -m pip install -U playwright    # Windows
# .venv/bin/python -m pip install -U playwright          # macOS/Linux
```

Если не помогло — временно переключитесь на Chromium: `browser.channel: ""` и `python run.py --install-browser`.

**Кажется, что скрипт «завис».** Долгие паузы ожидаемы: загрузка страницы hh.ru ждётся до 45 секунд,
ожидание карточек выдачи — до 15 секунд, плюс случайные паузы `delay_between_actions`. Прогресс печатается
в консоль («открываю вакансию», «LLM-решение», «LLM-вердикт», «отклик отправлен») и пишется
в `logs/<дата>.jsonl` (перезапуски дописывают в конец, событие помечено `run_id`). Если страница
не загрузилась, в консоли будет «Не удалось открыть поиск…»,
ошибка попадёт в отчёт, а для вакансий сохранится скриншот `logs/<run_id>-error-N.png`.

**Остановил приложение (Ctrl+C).** Это штатный сценарий: приложение дописывает отчёт, сохраняет сессию
и печатает итог вида «Работа приложения завершена, отправлено откликов: 2 из 3. Причина остановки: …
Сессия сохранена в …». Трейсбека быть не должно.

**Вакансия с тестом/анкетой, а в логе «отклик отправлен».** Статус отправки подтверждается
явным признаком на странице («Отклик отправлен» и т.п.). Если после нажатия «Откликнуться» появился экран
теста, анкеты или внешней формы — вакансия помечается в дневном отчёте как `queued` с причиной
«Для отклика на вакансию необходимо пройти тестирование» (или про анкету/сайт работодателя),
а запуск продолжается со следующей вакансии. Если подтверждения нет — причина
«hh.ru не подтвердил отправку отклика — проверьте вакансию вручную», подробности — в событии
`respond_state` и скриншоте `logs/<run_id>-respond-unknown.png`.

**Сколько откликов уже отправлено.** Лимит `limit_per_run` считает именно отправленные отклики:
отложенные вакансии лимит не расходуют. В строке отправки видно счётчик:
«отклик отправлен (всего N из M)».

**Резюме не поднимается.** Заполните `resume.name` — полное название резюме из списка резюме hh.ru.
Отметка о подъёме лежит в `data/cache.json`: если резюме поднимали меньше `resume.boost_interval_hours`
назад, приложение пишет об этом в лог и идёт дальше. Если кнопки «Поднять в поиске» нет (hh сам поднял
резюме) — подъём пропускается и кэш не обновляется.

**Каждый запуск требует входа заново.** Удалите `data/state.json` и выполните `sh run.sh --login` (или
`run.bat --login`): убедитесь, что вход в hh.ru завершён до нажатия Enter. Сессия живёт, пока hh.ru её не
сбросит; после сброса вход повторяется тем же способом.

**`data/state.json` больше мегабайта.** Так hh.ru хранит в localStorage кэш шрифтов
(`magritteFontsNewFont`, `xhhFontsFont`, `chatikFontsFont`) — около 1 МБ. Приложение при сохранении
сессии выбрасывает эти записи: для входа они не нужны, браузер скачивает шрифты заново. Файл
перезаписывается при каждом запуске (не дописывается), так что расти бесконечно он не может.

**hh.ru показал капчу.** Капча приходит и отдельной страницей, и модалкой «Пройдите капчу»
внутри формы отклика. Приложение её не обходит: печатает в консоль «hh.ru просит капчу: введите текст
с картинки в открытом окне браузера», сохраняет скриншот `logs/<run_id>-captcha.png` и ждёт до
`browser.captcha_wait_seconds` секунд. Введите текст и нажмите «Отправить» — отклик продолжится
с той же вакансии. Если не успели (или включён `headless: true`), вакансия помечается отложенной
с причиной «hh.ru просит пройти капчу: откликнитесь вручную», запуск останавливается. Дальше —
подождите 10–15 минут, уменьшите `limit_per_run` и увеличьте паузы `delay_between_actions`.

**Закрыли окно браузера во время работы.** Запуск останавливается с понятным сообщением, отчёт
сохраняется. Просто запустите снова — уже отработанные вакансии не попадут в отчёт второй раз.

**Ошибки LLM.** `HTTP 401` — неверный `AITUNNEL_API_KEY`; `HTTP 402` — закончился баланс AITUNNEL;
`HTTP 429`/`5xx` — временные лимиты, приложение делает пару повторов и продолжает работу.
Ответ не в формате JSON повторяется один раз, затем вакансия пропускается с ошибкой в отчёте.

**Письмо о капче не пришло.** Нужен тот же настроенный SMTP-канал, что и для отчёта
(`notifications.email.enabled: true` и `SMTP_PASSWORD` в `.env`), и включённый вид писем —
`notifications.captcha.enabled: true`. Проверьте канал командой `python run.py --notify-test`;
в JSONL событие `email_notify` с `sent: false` и причиной.
Сообщение «SMTP-сервер закрыл соединение» означает блокировку SMTP-входа у провайдера —
смените `smtp_host`/`sender` (см. раздел «Настройка»). Сбой отправки запуск не останавливает:
капча всё равно ждёт решения в окне браузера.

**Отчёт не пришёл на email.** Нужны `notifications.email.enabled: true` и
`notifications.report.enabled: true`, заполненные `smtp_host`,
`smtp_port`, `use_ssl`, `sender`, `recipient` и `SMTP_PASSWORD` в `.env`. Если отправка выключена или не
настроена, отчёт печатается в консоль и сохраняется в `logs/<run_id>.json` — данные не теряются.

**Кракозябры в консоли.** `run.bat` и `run.sh` сами включают UTF-8 (в `run.sh` `chcp` вызывается по
полному пути `C:/Windows/System32/chcp.com`). При запуске вручную через `python run.py` кодировку
терминала нужно выставить самому.

**«Не удалось разобрать config.yaml».** Ошибка YAML-синтаксиса: проверьте отступы и кавычки. JSON тоже
принимается, так как это подмножество YAML. Проверить конфиг без запуска: `python run.py --help` не
читает конфиг, а `python run.py --install-browser` — читает и покажет ошибку.

**Вакансий не найдено.** Проверьте `area`, `experience`, `schedule` (значения hh.ru: `between1And3`,
`remote`, …) и сам запрос; увеличьте `pages_limit`. Запрос с фильтрами можно посмотреть глазами:
откройте URL из лога.

**На сайте вакансий больше, чем в отчёте.** «Обработано вакансий» считает все карточки, которые
мы прошли, включая уже обработанные в прошлых запусках (`data/report`). Глубина выдачи —
`pages_limit × 20`: hh.ru отдаёт 20 карточек на страницу, поэтому для 44 вакансий нужен
`pages_limit: 3`. Сколько всего нашёл hh, видно в строке лога
«найдено 20 вакансий (hh.ru всего нашёл 44)».

## Ограничения

- Приложение не обходит капчу и не работает через API hh.ru.
- Отправка откликов автоматизирована: используйте на свой риск и соблюдайте правила hh.ru.
- Сессионные данные и переписка хранятся только локально; наружу уходят лишь запросы к LLM-провайдеру.
