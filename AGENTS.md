# AGENTS.md — соглашения проекта hh-agent

Агент автоматических откликов на hh.ru: Playwright (браузер, без API hh.ru) + AITUNNEL (Decision-вызов решает,
Generation-вызов пишет письмо). Работает по требованию: запуск → цикл → выход.

## Фундаментальные принципы

1. **Конфиг — единственный источник параметров.** Пороги, критерии, лимиты, модели и пути живут
   в `config.yaml`; в коде — только дефолты для тестов. Одно и то же число в двух местах — ошибка.
2. **Промпт компактный и дешёвый.** `SYSTEM_PROMPT.md` ≤ 3500 символов (проверяется тестом).
   Растить его можно только переформулировками и оптимизациями кода, не объёмом. Каждый вызов LLM
   должен быть оправдан по стоимости.
3. **Правда важнее стиля.** В письме только факты из профиля: лучше честно сказать «опыта нет»,
   чем выдумать технологию, цифру или проект.
4. **Данные пользователя локальны.** `data/` и `logs/` не попадают в git; наружу уходят только
   запросы к LLM-провайдеру.
5. **В логи не попадают чувствительные данные**: текст сопроводительного письма, профиль, контакты,
   токены, cookies. В JSONL — только факты и длины (`letter_length`), в консоль — понятный статус.
   Письмо живёт в памяти процесса и уходит на hh.ru.
6. **Один вызов — одна задача.** Decision даёт вероятности, Generation — письмо. При расхождении
   вердиктов побеждает Decision.

## Ключевые понятия

- **Decision**: ответ `answers.fit.probabilities`; отклик отправляется при `P("подходит") > llm.decision.threshold`.
- **Generation**: строгий JSON `{verdict, reason, cover_letter}`, ровно один повтор при невалидном JSON.
- **Критерии оценки** (`llm.decision.criteria`) и порог (`threshold`) описаны только в конфиге.
- **Подпись с контактами** добавляется кодом (`cover_letter_signature`) через пустую строку, модель её не пишет.
- **Приветствие** тоже гарантируется кодом (`ensure_greeting`): нет «Здравствуйте!» — добавляем,
  обрывок вроде «3PL.» в начале срезаем, факт пишем в лог (`greeting_added`). Промпт просит первое
  предложение «Здравствуйте! Заинтересовала Ваша вакансия.»; код гарантирует только «Здравствуйте!».
- **Обязательное начало письма**: если вакансия просит начать с конкретного слова («Начните сопроводительное письмо со
  слова 3PL»), `opening_from_text` находит его в описании,
  промпт получает явное требование, а `ensure_greeting(text, opening)` ставит приветствие сразу
  после этого слова («3PL. Здравствуйте! …») и не срезает его. Поле `required_opening` — в JSONL.
- **llm_reason** пишется в JSONL для одобрений и отказов: для отказов — из вероятностей (или текст модели при
  `explain_rejections: true`).
- **Дневные отчёты**: `data/report/<дата>.json` — пройденные вакансии, повторно не обрабатываются;
  файлы старше `processed_retention_days` удаляются при старте. Формат: шапка (`date`, `updated_at`,
  `summary` по статусам) и плоский список `vacancies`; другой формат (старые массивы) не читается —
  такие вакансии проходятся заново.
  Запись: `url`, `title`, `company`, `status` (`sent`/`skipped`/`queued`/`excluded`/`error`/`rejected`), `reason`
  (для всего, кроме `sent`; исключение — «отклик уже отправлен», см. ниже), `attempts`, `processed_at`; поиск идёт
  по `id` из URL, затем по
  «название + компания». Группировку по статусам не делаем: `status` уже в записи, а фильтр
  по плоскому списку — одна операция. Вакансия, не обработанная из-за лимита откликов, в отчёт
  не пишется — её пройдём в следующий раз.
- **Отклик уже отправлен**: hh.ru показывает, что отклик по вакансии уже есть (прошлый запуск или
  отклик руками). Такая вакансия пишется в файл дня со статусом `sent` и причиной «отклик уже отправлен»
  (`ALREADY_RESPONDED_REASON` в `agent/models.py`) — в вебе она в «Отправлено», а не в «Пропущено».
  Лимит `limit_per_run` и строка «Отправлено откликов» в отчёте запуска её не учитывают: отклик
  отправил не этот запуск. В JSONL — событие `already_responded` со `status: sent`.
- **Исключённые вакансии** (стоп-слово в `exclude_keywords` или компания из `exclude_companies`)
  получают `status: "excluded"`, а не `skipped`: их видно отдельной строкой отчёта и можно
  повторить, убрав слово или компанию из списка.
- **Состояния страницы вакансии** (`agent/hh_vacancy.py`): отметки «Вас пригласили», «Вам отказали»
  и заголовок «У вас нет доступа к этой вакансии» — это не отложенные вакансии, а пройденные.
  `detect_page_blocker` возвращает коды `invited` / `rejected` / `blocked`, `open_vacancy` сразу
  отдаёт их без разбора описания, а `PAGE_STATUS_REASONS` в `pipeline.py` превращает код в пару
  «статус + человеческая причина»: приглашение и недоступность — `skipped`, отказ работодателя —
  отдельный статус `rejected` с причиной «По отклику пришёл отказ» (`REJECTED_REASON` в
  `agent/models.py`). LLM для таких вакансий не вызывается, в JSONL — событие `page_status`.
- **Повторы** (`run.bat --retry`, в bash — `sh run.sh --retry`): идём сразу по `url` из дневных
  отчётов, без поиска и без фильтрации выдачи. Статусы для повтора — `retry.statuses` в конфиге (`error`, `queued`,
  `excluded`, можно добавить `skipped`); `--retry СТАТУС` сужает до одного,
  `--excluded` — синоним `--retry excluded`, `--re` — короткий алиас. Повтор обновляет запись (`attempts + 1`) и
  переносит её в файл сегодняшней даты. Дедупликация в режиме повтора
  не применяется.
- **Отложенные вакансии** живут в том же дневном отчёте (`status: "queued"`) с человеческой причиной
  из `QUEUE_REASON_TEXTS` (`test`, `questionnaire`, `external_form`, `empty_cover_letter`, `captcha`,
  `unknown`); отдельного `queue.json` нет. Код причины — только в JSONL (поле `code`).
- **Капча не обходится.** Она бывает страницей и модалкой «Пройдите капчу» внутри формы отклика (видна только по
  тексту). Приложение пишет в консоль просьбу решить её вручную и ждёт
  `browser.captcha_wait_seconds`; в headless-режиме не ждёт. Скриншот — `logs/<run_id>-captcha.png`,
  причина `captcha` в отчёте. О капче приходит **одно** письмо (`agent/notify.py`, тема
  `Необходимо пройти капчу на hh.ru`): вакансия и ссылка, без профиля, письма и контактов; дублей нет — повторная
  капча в той же попытке и остановка запуска второго письма не шлют. Сбой SMTP запуск
  не останавливает. Канал проверяется командой `python run.py --notify-test`, статус письма —
  событие `email_notify` (`sent`, `message`) в JSONL.
- **Виды писем** настраиваются раздельно: `notifications.report` и `notifications.captcha`
  (`enabled`, опциональный `recipient`; пусто — общий `notifications.email.recipient`).
  `notifications.email` — только транспорт (SMTP).
- **Подъём резюме** (`agent/resume.py`) выполняется сразу после входа и перед каждым следующим
  запросом из `search.queries` (`_process_vacancies` вызывает `boost_resume`, а тот сначала смотрит
  кэш): `resume.name` из конфига, не чаще `resume.boost_interval_hours`. Отметка — `data/cache.json`
  (`{название: время}`). Любая проблема со страницей логируется и не останавливает запуск.
- **Смена даты во время запуска**: запуск может идти через полночь, а журнал и дневной отчёт — файлы
  даты. `_check_new_day` вызывается перед каждым запросом и каждой вакансией: `RunLogger.switch_day`
  открывает `logs/<новая дата>.jsonl` (тот же `run_id`), `ProcessedStore.roll_to` переводит отчёт на
  файл новой даты, в консоль и событие `new_day` уходит одна строка. Дублей нет: при той же дате
  функция ничего не делает.
- **Сессия**: `data/state.json` — `storage_state` Playwright. При сохранении выбрасываем кэш шрифтов
  hh.ru (ключи, оканчивающиеся на `Font`): это ~1 МБ, для входа не нужен.
- **Выдача hh.ru**: `per_page` (20, 50 или 100) уходит в `items_on_page` без ограничения сверху —
  hh.ru отдаёт ровно столько карточек, сколько попросили. Глубина: `pages_limit` из конфига, а если
  он не задан — `ceil(найденных / per_page)`, но не больше `HH_MAX_PAGES` (50) и до первой пустой
  страницы. Число найденных читается из шапки первой страницы запроса, план пишется в лог
  («По запросу «Java developer» найдено 545 вакансий, разделяю обработку на 6 страниц») и в событие
  `search_pages_plan`; строка начала страницы — «Обработка 100 вакансий из результата запроса
  «Java developer»: страница 1 из 6».
- **Ленивая отрисовка карточек**: в DOM hh.ru сразу появляется первая двадцатка, остальные
  подгружаются порциями по 20 при прокрутке. `_load_all_cards` крутит страницу (окно и внутренние
  контейнеры с прокруткой) до конца, пока карточек не станет столько, сколько ждём, или пока список
  не перестанет расти `SCROLL_STABLE_SECONDS` (8 с). Ждать прироста обязательно: при коротком
  ожидании медленная страница обрезалась до 20 карточек. Сколько ждём, считает `expected_cards`:
  `per_page`, а на последней странице — остаток по «Найдено N» (350 при `per_page: 100` →
  100/100/100/50). Предохранитель — `SCROLL_TIMEOUT_SECONDS` (90 с) на страницу. Если карточек
  всё равно меньше, запуск пишет в консоль и в JSONL событие `search_page_short` (`cards`,
  `expected`): обрыв догрузки видно сразу, а не по числу обработанных.
- **Несколько значений фильтра** (`experience`) задаются списком в конфиге и уходят в URL
  повторяющимся параметром (`experience=a&experience=b`): hh.ru отмечает по ним несколько чекбоксов.

## Логи

- Консоль: `[ГГГГ-ММ-ДД ЧЧ:ММ:СС] [id] Название — Компания: событие` (`открываю вакансию`,
  `LLM-решение`, `LLM-вердикт`, `отклик отправлен`). Одна строка — одно событие, без повторов факта.
- `llm_verdict` — вердикт приложения (после порога), `model_choice` — вариант модели с максимальной
  вероятностью. Одно и то же число дважды в консоль не печатаем.
- JSONL `logs/<дата>.jsonl`: один файл на дату, перезапуски дописывают в конец; `run_id` в каждой
  записи отделяет запуски. В событии — имя события + `vacancy` (без номера) + `vacancy_id` +
  `llm_reason` + детали (URL, вероятности, длина письма). Текст письма, профиль и контакты
  в логи не пишутся.
- Отдельного файла деталей запуска нет: итоги — в консоли и письме, по вакансиям — в дневном
  отчёте, события — в JSONL.
- Отчёт: шапка из `=`, ниже пункты `- Ключ: значение`, печатается без меток времени (`info_plain`);
  списка отправленных вакансий в нём нет — он в файле дня.
- Пользователю печатаем понятный текст, технические детали уходят в JSONL.

## Код

- Python 3.11+, зависимости только на wheels (без сборки C++): `playwright`, `httpx`, `ruamel.yaml`, `python-dotenv`.
- Пакет приложения — `agent/` (запуск через `run.py`, поэтому дублирования имени проекта в пути нет).
- Русские докстринги и сообщения; `from __future__ import annotations`; frozen dataclass для конфигурации и моделей.
- Ошибки браузера — `PlaywrightError`; потеря сессии hh.ru — `SessionLostError`; сбои LLM — `LLMError`.
- Внутренние модули: `config`, `browser`, `hh_search`, `hh_vacancy`, `llm`, `prompts`, `pipeline`,
  `processed`, `resume`, `report`, `notify`, `logging_setup`, `profile`, `cli`.
- Веб-интерфейс отчётов — отдельное приложение `web/` (FastAPI + Jinja2): читает и правит
  `data/report`, агент от него не зависит. Правка статуса меняет только нужные поля: для
  `rejected` (отказ работодателя) — `status`, `reason` («По отклику пришёл отказ») и `processed_at`
  без пересчёта попыток, для остальных статусов — `status`, `attempts` (+1) и `processed_at`;
  итоги в шапке пересчитываются по записям. В хедере один выбор — дата
  (дропдаун с чекбоксами, можно несколько или все): дата и файл дня — одно и то же, поэтому
  значения чекбоксов — имена файлов. Список файлов даёт `GET /api/v1/reports`,
  вакансии — `GET /api/v1/vacancies?files=a.json,b.json` (без `files` — все файлы).
- Документация: `README.md` — быстрый старт и ссылки; подробности — `docs/`; параметры — комментарии
  в `config.yaml` (не дублируем их в `.md`); соглашения разработки — этот файл.

## Тесты и проверки

- Перед завершением задачи: `pytest -q` зелёный и `pyflakes agent run.py tests` без замечаний.
- Новая логика — новый тест. Сеть только через `httpx.MockTransport`, браузер в тестах не запускается.

## Окружение

- Windows: `py` и `.venv\Scripts\python.exe` (в PATH `python` — заглушка Microsoft Store).
  Запуск: `run.bat`; в bash/WSL — `sh run.sh`.
- Коммиты делает пользователь. Агент не коммитит, не меняет `.env` и не печатает секреты.

## Границы

- Не обходим капчу, не используем API hh.ru, соблюдаем правила сайта.
- Не переименовываем ключи конфига без обратной совместимости (пример: `daily_limit` → `limit_per_run`).
