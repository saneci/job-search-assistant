# AGENTS.md — соглашения проекта hh-agent

Агент автоматических откликов на hh.ru: Playwright (браузер, без API hh.ru) + LLM-провайдер (Decision решает, Generation
пишет письмо). Работает по требованию: запуск → цикл → выход.

## Начало работы: отчёт истории ветки

> [!IMPORTANT]
> **Первым делом открой отчёт истории своей ветки, до чтения кода и любой другой документации**

1. Отчёт лежит в `.agents/history/<ветка>/<yyyy-mm-dd>.md`, каталог называется по git-ветке: слэши заменяются
   дефисами, вложенных каталогов нет, ветка `fix/process-archive-vacancies` даёт каталог
   `.agents/history/fix-process-archive-vacancies/`
2. Отчёт — отправная точка: что уже сделано, что не сделано, техдолг и замеченные расхождения
3. Затем читай спецификации фич в [docs/features](docs/features) — только те, что относятся к задаче
4. Затем смотри тесты: они описывают ожидаемое поведение и текущие договорённости
5. Только после этого читай и меняй код бизнес-логики

Проверки из отчёта повторно не выполняй, если с тех пор ничего не менялось. После завершения цикла обнови тот же
файл отчёта: другой агент начнёт с него.

## Базовые принципы

> [!IMPORTANT]
>  **Если тест или команда падает дважды, остановись и спроси меня, больше не создавай временные файлы**

1. Конфиг — единственный источник параметров. Поведение — в `config.yaml`, личные данные — в `config.local.yaml`,
   секреты — в `.env`. В коде только дефолты схемы. Одно и то же значение в двух местах — ошибка.
2. Промпт компактный. `SYSTEM_PROMPT.md` ≤ 3500 символов (проверяется тестом).
3. Правда важнее стиля. В письме только факты из профиля: лучше «опыта нет», чем выдумка.
4. Данные пользователя локальны. `data/`, `.env`, `config.local.yaml` не в git.
5. Чувствительные и секретные данные не логируются и не хранятся в в git: текст письма, профиль, контакты, токены,
   cookies и другая информация которая является персональными данными согласно Федерального закона № 152-ФЗ «О
   персональных данных».
6. Один вызов — одна задача. LLM Decision даёт вероятности, LLM Generation — сопроводительное письмо. При расхождении
   вердиктов побеждает Decision.
7. Если документация репозитория противоречит существующему коду - следуй соглашениям, принятым в самом коде, а в
   финальном ответе укажи каждое найденное несоответствие между документацией и кодом.
8. Ничего сверх задания без согласования. Не делать того, что не указано прямо в задании. любое расширение объёма
   работ — только после явного согласия пользователя.
9. В конце задания — замеченное и план доработки. Они пишутся в отчёт истории (правило 12), а не в чат, с
   обоснованием причин. В чате текст отчёта не дублируется.
10. Длина строки — не больше 120 символов. Для всех `*.md` документов проекта. Исключение — строки Markdown-таблиц:
    выравнивание колонок важнее лимита.
11. Прежде чем усложнять решение ради гипотетической гонки состояний или крайне маловероятного сценария, связанного с
    безопасностью, сначала объясни пользователю, в чём именно может проявиться проблема, насколько она вероятна и какой
    ценой обойдётся это усложнение. Получи его согласие. Не расширяй объём задачи молча лишь ради теоретической
    надёжности.
12. После выполнения задачи создай отчёт в `.agents/history/<ветка>/`, чтобы новый агент мог продолжить работу
    с этого места. Каталог называется по git-ветке: слэши заменяются дефисами, вложенных каталогов нет, например
    ветка `fix/process-archive-vacancies` даёт `.agents/history/fix-process-archive-vacancies/`. Формат файла:
    `<yyyy-mm-dd>.md`. Если дневной отчёт уже есть, актуализируй информацию: удали неактуальную, допиши новые
    сведения если требуется. Если дневного отчёта ещё нет - создай. Отчёт должен содержать только актуальную
    информацию по итогам работы и разделы: «Цель», «Что сделано», «Проверки», «Замечено и не исправлено»,
    «План доработки»
    После выполнения работ в чат пиши только одно предложение:
    `Работы завершены, отчёт сохранил в <path>/<file-name>`. Исключение — прямые вопросы пользователя по
    задаче: на них отвечаем кратко в чате, без пересказа отчёта

## Границы задач

- Только текущий проект: запрещено читать или изменять файлы за пределами текущего проекта
- Никакой избыточности: не делай работу, которая не требуется для решения текущей задачи - не ломай обратную
  совместимость (API, интерфейсы, форматы данных)
- Согласование (Stop & Ask): обязательно останавливайся и согласовывай со мной решение, если:
    - в задаче есть неочевидные детали или пробелы
    - требуются доработки, выходящие за рамки текущей задачи

## Документация и контекст

### Перед изменением кода обязательно ознакомься со спецификацией фичи

1. Определи, к какой фиче относится задача (по названию компонента, файла или сути запроса)
2. Найди соответствующую папку в [docs/features](docs/features) и прочитай только файл `spec.md` внутри неё
3. Не читай спецификации других фич, если они не связаны с текущей задачей - экономь контекст
4. Если спецификации для задачи нет — сначала предложи её создать

### Правила работы с документацией

- Не дублируй в `spec.md` реализацию из кода (структуры, API), разделяй по функциональности и смыслу, спека — это
  бизнес-логика и критерии
- Если код противоречит спеке, уточни у пользователя, что является истиной
- В тексте Markdown-документов не используй `;`, только точки и запятые
- Не используй в списках (разметка `-`, `*` или порядковые номера пунктов) в конце точки `.`
- Не пиши в списках по несколько предложений, смысл связывается, там где уместно по правилам русского языка, двоеточием
  `:`, запятой `,` или с помощью `-`, новое предложение - новый элемент списка
- В финальном ответе обязательно перечисли каждое найденное несоответствие между документацией и кодом, если такое было
  обнаружено, не выдумывай если нет
- Заметки и подсказки в документации (`docs/**`, `README.md`, `.plans/**`, etc.) оформляются admonition-блоками GitHub:
  ```markdown
  > [!TIP]
  > Короткая подсказка

  > [!NOTE]
  > Пояснение
  ```
  Доступны `[!NOTE]`, `[!TIP]`, `[!IMPORTANT]`, `[!WARNING]`, `[!CAUTION]`. Строки вида «Замечание:» и ручное
  выделение жирным для акцентов не используем.

## Код

- Используй скилл `tdd`, если его нет в локальном окружении - установи командой:
  `npx -y  skills add https://github.com/mattpocock/skills --skill tdd --agent cline --yes`
- Python 3.11+, только wheels: `playwright`, `httpx`, `ruamel.yaml`, `python-dotenv`, `pydantic`, `pydantic-settings`.
- Пакет `agent/`, запуск через `run.py`
- Русские докстринги и сообщения, `from __future__ import annotations`, frozen-модели
- Ошибки: `PlaywrightError`, `SessionLostError`, `LLMError`, `ConfigError`
- Модули: `config`, `channel`, `browser`, `hh_search`, `hh_vacancy`, `habr_search`, `habr_vacancy`, `llm`, `prompts`,
  `pipeline`, `processed`, `resume`, `report`, `notify`, `logging_setup`, `profile`, `cli`
- Веб-интерфейс `web/` — отдельное приложение, агент от него не зависит
- Докстринг объясняет, зачем нужен класс или функция, и неочевидные технические моменты: не пересказывает, что делает
  код, и не дублирует бизнес-требования из `docs/features/**/spec.md`. Если без текста всё понятно, докстринг не нужен
- Докстринги тестов — исключение: в них описывается проверяемое поведение
- Однострочные комментарии `# ...` в коде запрещены: код пишется так, чтобы они не требовались, а пояснение уходит
  в докстринг. Служебные директивы (`# type: ignore`, `# noqa`) допустимы

## Логи

- Консоль: одна строка — одно событие, понятный пользователю текст
- `data/logs/<дата>.jsonl`: `run_id`, событие, вакансия, причины, вероятности, длины. Текста письма и личных данных нет
- `run_id` — идентификатор запуска в едином формате `ГГГГММДДЧЧММСС` (`20261021170519`), один на запуск,
  у агента и веб-интерфейса формат один. Правка статуса из UI отличается полем `event: ui_status_update`
- `data.logs_retention_days` чистит только логи. Отчёты остаются навсегда

## Тесты и проверки

- Перед завершением: `pytest -q` и `pyflakes agent run.py tests web` - без замечаний
- Новая логика - новый тест. Существующие тесты не меняются: упавший тест - регрессия, исправляется код, а не тест
- Тесты конфига - таблицами `parametrize`: дефолты, ошибки, приоритет источников
- Запуск проверок, покрытие инструментов и правила оформления тестов в [docs/how-to/testing.md](docs/how-to/testing.md)

## Git и изменения

- Коммиты запрещены. Ты можешь только читать состояние репозитория (`git status`, `git diff`). Писать в Git (commit,
  push) разрешается только когда есть прямое указание от меня
- Параллельная разработка. В соседних ветках ведется активная работа. Вноси изменения предельно точечно и
  внимательно, чтобы минимизировать будущие конфликты при слиянии

## Ошибки

- Баги фиксируются в GitHub Issues, а не в документации
- Баг-репорт всегда оформляется текстовым блоком: сначала описание, затем список «Серьёзность», «Предусловия»,
  «Ожидаемый результат», «Фактический результат»
