# AGENTS.md — соглашения проекта hh-agent

Агент автоматических откликов на hh.ru: Playwright (браузер, без API hh.ru) + LLM-провайдер (Decision решает, Generation
пишет письмо). Работает по требованию: запуск → цикл → выход.

## Базовые принципы

1. **Конфиг — единственный источник параметров.** Поведение — в `config.yaml`, личные данные — в `config.local.yaml`,
   секреты — в `.env`. В коде только дефолты схемы. Одно и то же значение в двух местах — ошибка.
2. **Промпт компактный.** `SYSTEM_PROMPT.md` ≤ 3500 символов (проверяется тестом).
3. **Правда важнее стиля.** В письме только факты из профиля: лучше «опыта нет», чем выдумка.
4. **Данные пользователя локальны.** `data/`, `logs/`, `.env`, `config.local.yaml` не в git.
5. **Чувствительные и секретные данные не логируются и не хранятся в в git**: текст письма, профиль, контакты, токены,
   cookies и другая информация которая является персональными данными согласно Федерального закона № 152-ФЗ «О
   персональных данных».
6. **Один вызов — одна задача.** LLM Decision даёт вероятности, LLM Generation — сопроводительное письмо.
   При расхождении вердиктов побеждает Decision.
7. **Если документация репозитория противоречит существующему коду** - следуй соглашениям, принятым в самом коде, а в
   финальном ответе укажи каждое найденное несоответствие между документацией и кодом.
8. **Ничего сверх задания без согласования.** Не делать того, что не указано прямо в задании.
   любое расширение объёма работ — только после явного согласия пользователя.
9. **В конце задания — замеченное и план доработки.** Всегда выводить, что замечено и что нужно
   доработать, с обоснованием причин.
10. **Длина строки — не больше 120 символов.** Для всех `*.md` документов проекта. Исключение — строки
    Markdown-таблиц: выравнивание колонок важнее лимита.

## Правила разработки и ограничения

### Git и изменения

- **Коммиты запрещены.** Ты можешь только читать состояние репозитория (`git status`, `git diff`). Писать в Git (commit,
  push) разрешается только когда есть прямое указание от меня.
- **Параллельная разработка.** В соседних ветках ведется активная работа. Вноси изменения предельно точечно и
  внимательно, чтобы минимизировать будущие конфликты при слиянии.

### Границы задач

- **Только текущий проект.** Запрещено читать или изменять файлы за пределами текущего проекта.
- **Никакой избыточности.** Не делай работу, которая не требуется для решения текущей задачи. Не ломай обратную
  совместимость (API, интерфейсы, форматы данных).с
- **Согласование (Stop & Ask).** Обязательно останавливайся и согласовывай со мной решение, если:
    - В задаче есть неочевидные детали или пробелы.
    - Требуются доработки, выходящие за рамки текущей задачи.

## Документация и контекст

**Перед изменением кода** обязательно ознакомься со спецификацией фичи:

1. Определи, к какой фиче относится задача (по названию компонента, файла или сути запроса).
2. Найди соответствующую папку в [docs/features](docs/features) и прочитай **только** файл `spec.md` внутри неё.
3. Не читай спецификации других фич, если они не связаны с текущей задачей (экономия контекста).
4. Если спецификации для задачи нет — сначала предложи её создать.

**Правила работы с документацией:**

- Разделение: Не дублируй в `spec.md` реализацию из кода (структуры, API). Спека — это бизнес-логика и критерии.
- Конфликты: Если код противоречит спеке, уточни у пользователя, что является истиной.
- Стиль: В тексте Markdown-документов не используй `;`. Только точки и запятые.
- Отчет о расхождениях: В финальном ответе обязательно перечисли каждое найденное несоответствие между документацией
  и кодом.

## Код

- Python 3.11+, только wheels: `playwright`, `httpx`, `ruamel.yaml`, `python-dotenv`,
  `pydantic`, `pydantic-settings`.
- Пакет `agent/`, запуск через `run.py`.
- Русские докстринги и сообщения, `from __future__ import annotations`, frozen-модели.
- Ошибки: `PlaywrightError`, `SessionLostError`, `LLMError`, `ConfigError`.
- Модули: `config`, `channel`, `browser`, `hh_search`, `hh_vacancy`, `habr_search`,
  `habr_vacancy`, `llm`, `prompts`, `pipeline`, `processed`, `resume`, `report`, `notify`,
  `logging_setup`, `profile`, `cli`.
- Веб-интерфейс `web/` — отдельное приложение, агент от него не зависит.

## Логи

- Консоль: одна строка — одно событие, понятный пользователю текст.
- `logs/<дата>.jsonl`: `run_id`, событие, вакансия, причины, вероятности, длины.
  Текста письма и личных данных нет.
- `data.logs_retention_days` чистит только логи. Отчёты остаются навсегда.

## Тесты и проверки

- Перед завершением: `pytest -q` и `pyflakes agent run.py tests web` без замечаний.
- Новая логика — новый тест. Существующие тесты не меняются: упавший тест — регрессия,
  исправляется код, а не тест.
- Тесты конфига — таблицами `parametrize`: дефолты, ошибки, приоритет источников.
- Запуск проверок, покрытие инструментов и правила оформления тестов —
  в [docs/how-to/testing.md](docs/how-to/testing.md).

## Ошибки

- Баги фиксируются в GitHub Issues, а не в документации.
- Баг-репорт всегда оформляется текстовым блоком: сначала описание, затем список «Серьёзность»,
  «Предусловия», «Ожидаемый результат», «Фактический результат».

## Окружение

- Windows: `py` / `.venv\Scripts\python.exe`, `run.bat`. Bash/WSL — `sh run.sh`.
- Коммиты делает пользователь. Агент не коммитит, не меняет `.env` и не печатает секреты.

## Границы

- Капчу не обходим, API hh.ru не используем, правила сайта соблюдаем.
- Публичные ключи конфига меняем только явным решением: формат один.
